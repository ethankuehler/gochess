# AGENTS.md

## Project overview

`gochess` is a personal, work-in-progress chess engine written in Go. The author
is using it to learn Go; per the README it is "not close to done". There is no
engine search or UCI protocol yet — the codebase currently consists of board
representation, FEN handling, and attack-table generation/lookup.

- Module: `github.com/ethankuehler/gochess` (see `go.mod`, `go 1.23.2`)
- Dependencies: Go standard library only. There is no `go.sum`.
- Packages:
  - `main` (repo root, `main.go`) — a scratch/demo binary that builds attack
    tables, parses a FEN, and prints boards. Not a real application yet.
  - `chess` (`chess/`) — the actual library. All engine logic lives here.
  - `cmd/genmagics` (`cmd/genmagics/`) — CLI that regenerates the magic-number
    CSVs in `data/`.

## Repository layout

- `main.go` — demo entry point (`package main`).
- `cmd/genmagics/main.go` — regenerates `data/rook_magics.csv` and
  `data/bishop_magics.csv`; run from the repo root.
- `chess/` — the engine library (`package chess`):
  - `BitBoard.go` — `BitBoard` (`uint64`) type, `BoardState` struct, validated
    FEN parse/serialize (`NewBoardFEN`, `FEN()`), board printing (`String`,
    `StringUni`), `Occupied`, `GetPieces`. `LegalMoves()` is a TODO stub that
    returns nil.
  - `Const.go` — `Shift`, `Coordinates`, `Piece` and `Colour` enums, bit masks
    for turn/castling encoding, piece symbol tables.
  - `Move.go` — `Move` struct with `From`/`To`/`Promotion` accessors,
    `NewMoveUCI` (including promotion suffixes), and algebraic-notation
    conversions (`LocFromAlg`, `AlgFromLoc`, `ShiftFromAlg`, `ShiftIter`).
  - `Magic.go` — precomputed attack tables (knight, king, pawn) loaded from
    CSV, `RayCast` for sliding pieces, and magic-bitboard generation/lookup
    for rooks and bishops (`MagicEntry`, `FindMagic`, `TryMagic`,
    `RelevantBlockers`, `GetRookAttack`, `GetBishopAttack`, `GetQueenAttack`).
  - `Utils.go` — CSV loading (`LoadAttacks`) for the attack tables, plus
    magic-number save/load (`SaveMagics`, `LoadMagics`).
- `data/` — generated/test data, loaded at runtime via **relative** paths:
  - `knight_attacks.csv`, `king_attacks.csv`, `white/black_pawn_move.csv`,
    `white/black_pawn_attacks.csv` — attack tables (columns: index, start
    square bit, move bitboard), generated by `display_binary.py`.
  - `rook_magics.csv`, `bishop_magics.csv` — magic numbers for the sliding
    pieces (columns: square, mask, magic), written by `SaveMagics` (not by
    `display_binary.py`).
  - `FEN.csv` — FEN corpus used as test fixtures.
  - `raycast_examples.json`, `bishop_mask_examples.json` — JSON test fixtures.
- `display_binary.py` — Python 3 script that regenerates the CSV attack
  tables in `data/`. Requires `pandas`. Run from the repo root
  (`python3 display_binary.py`); it writes to `data/*.csv`.
- `.vscode/launch.json` — VS Code debug config for `main.go`.

## Build and test commands

```sh
go build ./...     # build everything
go run .           # run the demo binary (must run from repo root)
go run ./cmd/genmagics  # regenerate data/*_magics.csv (must run from repo root)
go test ./...      # run all tests
go vet ./...       # (optional) static checks
```

Working directory matters: the `chess` package's `Build*` functions and the
tests open `data/...` via relative paths. Run the binary and tests from the
repo root. The test suite handles this itself with a `TestMain` in
`chess/BitBoard_test.go` that `os.Chdir("..")`s to the repo root — preserve
that pattern if you add tests that touch `data/`.

There is no CI, linter config, or deployment process. The compiled `gochess`
binary, `.vscode/`, `.github/`, and some planning notes
(`MAGIC_BITBOARD_PLAN.md`, `CODE_REVIEW.md`) are gitignored.

## Core conventions and architecture

Bitboard representation:

- `BitBoard` is a `uint64`; square mapping is little-endian rank-file:
  bit 0 = a1, bit = `col + row*8`, bit 63 = h8. `Shift` is the square index.
- `Shift` is the canonical square representation; `Coordinates` and
  single-bit `BitBoard` "Locs" are converted at the edges via
  `CoordsFromShift` / `ShiftFromCoords` / `LocFromAlg`. Always build
  `Coordinates` with named fields (`Coordinates{row: ..., col: ...}`) —
  positional literals are a transposition hazard since the field order is
  row-first.
- `BoardState.pieces` is a `[12]BitBoard` array: indices 0–5 are white
  PAWN, BISHOP, KNIGHT, ROOK, QUEEN, KING; black pieces are the same order
  offset by `BLACK_OFFSET` (6).
- `BoardState.encoding` (uint8) packs side-to-move (`TURN_MASK`) and the four
  castling rights (`WHITEOO_MASK`, `WHITEOOO_MASK`, `BLACKOO_MASK`,
  `BLACKOOO_MASK`). En passant is a single-square `BitBoard`, not an index.
- Piece attack tables are `[]BitBoard` of length 64 indexed by `Shift`,
  populated from the CSVs by `BuildKnightAttacks` / `BuildKingAttacks` /
  `BuildPawnMoves` / `BuildPawnAttacks` (or all at once via
  `BuildAllAttacks`). Sliding-piece (rook/bishop) magic tables are
  restored from `data/*_magics.csv` by default (`LoadMagicsFromDisk`),
  rebuilt with `TryMagic` to validate the stored magics. If a CSV is
  missing or invalid, the builder logs a message and falls back to a
  random magic search; setting `SaveMagicsToDisk` rewrites the CSVs after
  a search (normally done via `go run ./cmd/genmagics`). Queens reuse the
  rook and bishop lookups via `GetQueenAttack`.

Go style used in this repo:

- Uses Go 1.22+ features: `iter.Seq` iterators (`PiecesIter`, `ShiftIter`)
  and `math/rand/v2`. Keep compatibility with the `go 1.23.2` directive.
- Mixed exported/unexported identifiers; struct fields are mostly
  unexported with snake_case names (e.g. `halfmove_clock`).
- Error handling is plain `errors.New` / `fmt.Errorf`; CSV loaders and
  `ShiftIter` use `log.Fatal`; `GetPieces` panics on invalid input. Match
  the surrounding style when editing nearby code.

Things to be careful with:

- Several exported names contain typos that are load-bearing across files —
  e.g. `PICECES_SYM`, `UNI_PICECES_SYM`, `ROOK_ATTTACKS`, `enpassant`. Do not
  rename them as a drive-by fix; a rename must update every reference.
- `TryMagic` uses a zero table slot as "not yet written"; that sentinel is
  safe only because rook/bishop attack sets are never empty. Keep that
  invariant in mind before reusing the pattern elsewhere.
- `NewBoardFEN` is strict: it requires 8 ranks of 8 squares, exactly one king
  per side, at most 16 pieces and 8 pawns per side, no pawns on the back
  ranks, a fullmove number of at least 1, and an en passant square on rank 3
  or 6. `NewBoardDefault` uses the standard start position (`... 0 1`).
- `display_binary.py` is a one-off generator script, not part of the Go
  build; the CSVs it writes are committed and treated as source data.

## Testing instructions

- Tests live in `chess/*_test.go` using the standard `testing` package;
  run with `go test ./...`.
- Tests are data-driven: FEN round-trip tests read `data/FEN.csv`, raycast
  and bishop-mask tests read the JSON fixtures in `data/`. Add new cases by
  extending those files rather than hardcoding positions, where practical.
- Current suite covers FEN parse/serialize round-trips, rejection of
  malformed FENs (placement, kings, pawns, clocks, castling, en passant),
  the default board setup, `Occupied`, `SquaresToBitBoard`, UCI move
  round-trips (including promotions and invalid moves), pawn table loading,
  `RayCast`
  (fixtures plus an exhaustive reference comparison), `GetBishopMask`,
  `RelevantBlockers` popcounts, magic rook/bishop/queen lookups checked
  against `RayCast` for all squares with random blocker boards, a magic
  save/load round-trip, disk restore by default (`LoadMagicsFromDisk`),
  the missing-CSV fallback path, `BuildAllAttacks`, and rejection of
  malformed magic CSVs.
- There is no test coverage for move application or `LegalMoves` yet
  (unimplemented).

## Security considerations

- No network code, no external services, no secrets, no third-party Go
  modules — the attack surface is essentially nil.
- Runtime input is limited to FEN/UCI strings and the local `data/` files;
  the parsers return errors on malformed input and are unit-tested against
  invalid cases, but they are not fuzzed.
  `display_binary.py` requires `pandas` if you regenerate the CSVs — install
  it in a virtual environment, not system-wide.
